相談はだいたい同じ形で届きます。プロダクトは動いていた。アーキテクチャは誰も変えていない。それなのに一覧画面に9秒かかり、モバイルアプリはエクスポートでタイムアウトし、しかも特定の顧客の特定の画面ではなく全員に起きている。

壊れたものは何もありません。データ量が増え、定数時間だった誤りが線形時間の誤りになっただけです。1,000件のテーブル全件読み取りは何の費用でもありませんが、10万件ではそれがプロダクトそのものになります。

本番のSaaSでこれを腰を据えてやったとき、原因は5つのパターンに整理できました。どれも単体なら致命傷になりませんが、たいてい同時に現れて重なります。

## 調べる順番

直す前に、この順番で見ます。逆から見ると、速いはずのものが速いことを確認して終わります。

1. **コード。** すべての読み取り経路を。リゾルバーやメソッドの名前ではなく、実際に発行されているクエリを。
2. **クエリ。** 本物のパラメータで、本物のデータ量に対してプロファイルしたもの。シードデータで速いクエリは何も教えてくれません。
3. **CloudWatch。** 時間軸での挙動。遅い操作と遅い**パターン**を区別するために使います。

ドキュメントは最後です。ドキュメントは誰かが意図したモデルを説明し、コードと動いているシステムは実際にあるモデルを説明します。

## パターン1: QueryでよいところのScan

`Scan`はテーブル全体を読んでから絞り込みます。フィルタは読み取りの**後**に動くので、3件しか返さない`Scan`も、時間と容量の両方で支払う分はすべて読み終えています。

```ts
// 全件読んでから1テナント分に絞る。RCUは全件分かかる
await ddb.send(new ScanCommand({
  TableName: 'Jobs',
  FilterExpression: 'tenantId = :t',
  ExpressionAttributeValues: { ':t': { S: tenantId } },
}));

// キーに行って必要な分だけ読む
await ddb.send(new QueryCommand({
  TableName: 'Jobs',
  KeyConditionExpression: 'tenantId = :t',
  ExpressionAttributeValues: { ':t': { S: tenantId } },
  Limit: 20,
}));
```

**確認方法**: コード中の`Scan`をすべて探し、それぞれについて「代わりにどのキーで`Query`するか」を書き出します。キーを挙げられなければ、見つかったのはクエリの問題ではなくキー設計の問題です（パターン3）。

`ReturnConsumedCapacity: 'TOTAL'`を付けて実際のRCUを見ると、議論が早く終わります。

## パターン2: GSIがない

GSIは、よく使うアクセスパターンにプライマリキー以外の経路を与えるためにあります。これがないと「この顧客の注文を新しい順に」に答える方法は`Scan`か、必要以上の件数を読むかしかありません。

**確認方法**: 画面が実際に投げている問いを、日本語の文のまま書き出します。

- 「このテナントの案件を更新日の新しい順に20件」
- 「このステータスの案件を全テナント横断で」
- 「この担当者に割り当てられた案件を」

そのひとつひとつが、キーかインデックスに対応するはずです。どちらにも対応しないものが、作るべきGSIのリストです。

## パターン3: 読まれ方と一致しないキー

これは実際には再設計で、だからこそパターン1と2が何度も戻ってきます。

パーティションキーが「読み取りがそれで束ねられるから」ではなく「分かりやすい識別子だったから」という理由で選ばれていると、すべての読み手が永遠に回避策を書き続けることになります。

**確認方法**: アクセスパターンごとに、欲しい項目が隣り合っているかを問います。答えが「散らばっていてフィルタしている」なら、キーが間違っています。

ここだけは、直すとデータ移行になります。移行の計画は[別のノート](https://aligator527.github.io/ja/notes/release-plan-is-a-return-plan/)に書きました。

## パターン4: リゾルバーのN+1

AppSyncでも、ほかのGraphQL層でも、一覧のフィールドは1回だけ解決され、入れ子のフィールドは**項目ごとに**1回ずつ解決されます。50件の一覧を取る1リクエストが51リクエストになります。

```graphql
query {
  jobs(limit: 50) {       # 1回
    items {
      id
      customer { name }   # 50回
    }
  }
}
```

リゾルバーは単体では正しいので、コードは無害に見えます。

**確認方法**: 一覧画面1つあたりの**時間**ではなく、リクエストの**本数**を数えます。その本数は一覧の長さとともに増えてはいけません。増えるなら、`BatchGetItem`に寄せるか、親の読み取りで必要な項目を持たせるかの二択です。

## パターン5: ページングなしで全件をクライアントへ

画面は20行を表示し、リクエストはテーブルにあるすべてを返す。いちばん見つけやすく、いちばん直しやすく、だからこそ何年も生き延びます。問題が起きるその日までは遅く見えないからです。

**確認方法**: 所要時間ではなく、レスポンスの**サイズ**を見ます。開発者ツールのNetworkタブで1画面あたり数MBが返っていれば、それです。

`Limit`と`ExclusiveStartKey`（AppSyncなら`nextToken`）を通すのは一日の作業ですが、UIが「全件前提」で書かれていると、そちらのほうが大きな仕事になります。

## やらないこと

- **最初の一手としてのシングルテーブル全面再設計。** 最終的な姿としては正しいことが多く、最初の一手としてはほぼ正しくありません。いちばん理解できていない対象に、症状がまだ説明できていないうちに、可能な限り大きな変更を加えることになります。
- **Scanの前にキャッシュを置くこと。** グラフは良く見えるようになり、費用はまったく同じ場所に残り、その上に鮮度の問題が乗ります。
- **測り方を決める前に数字を追うこと。** 何を、どの操作で、どのデータ量で測るのかを先に決めないと、改善とノイズの区別がつきません。

## チェックリスト

```text
[ ] Scan をすべて洗い出し、各々に代替のキーを書いた
[ ] 画面の問いを文で書き出し、キー／インデックスに対応づけた
[ ] アクセスパターンごとに、項目が隣り合っているかを確認した
[ ] 一覧画面1つのリクエスト本数を数えた（長さに比例していないか）
[ ] 1画面あたりのレスポンスサイズを見た
[ ] 測定の対象・操作・データ量を、変更前に決めた
```
