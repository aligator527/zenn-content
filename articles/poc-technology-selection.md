「うちが慣れているから」で守られる技術選定は、正しいこともありますが、検証できることは決してありません。PoC（技術検証）はそれを検証可能にします。ただし、プロダクトの早期バージョンとしてではなく、判断の手続きとして回した場合に限ります。

消費者向けプロダクトの新規立ち上げでバックエンドの言語を決めたとき、好みではなく複数のPoCを経てGoを選びました。そのときに使った型と、いま足すべき4つ目の評価軸を書きます。

## PoCが満たすべき3条件

プロトタイプと分けるものは3つです。

1. **「いいえ」と答えてよい問い**
2. **誰かがコードを書き始める前に合意された評価軸**
3. **終わる日付**

どれか1つでも欠けると、PoCは静かにシステムの初版になります。デモがそのまま出荷され、問いは誰も読み返さず、スタックはサンクコストによって決まります。

問いは失敗できる形でなければなりません。

```text
NG: 「Xで作れるか？」        → 時間さえあれば答えは常に「はい」
OK: 「本当に不安な部分について、Xは2日で何を要求してくるか？」
```

## 比較を比較可能にする

同じ課題、同じ期限、同じレビュアー。課題には、実際に不安なものを選びます。気になっているクエリ、並行処理、ドキュメントが薄そうな連携先。どの候補でも同じように書けるCRUDエンドポイントではありません。

うまくいかなくなる道は3つ、どれもよくある形です。

| 失敗の形 | 何が起きるか |
|---|---|
| 候補ごとに、推している人が実装する | 実装の熱量差が、技術の差として記録される |
| 候補によって使える時間が違う | 先に着手したほうが有利になる |
| 評価軸が結果のあとに書かれる | 驚くほど勝者に合っている |

## 評価軸は4つ、すべて「答えの出る問い」に変える

形容詞のままにすると会議で溶けます。数字か、手順に落とします。

| 評価軸 | 形容詞のまま | 答えの出る問いに変える |
|---|---|---|
| スケーラビリティ | 「スケールする」 | 想定の10倍・100倍の負荷で何が起き、そこでいくらかかるか |
| 保守性 | 「読みやすい」 | 書いていない人が小さな変更を安全に入れるまでの時間 |
| 速度 | 「速い」 | システムの速度と、チームが流暢に書ける速度の両方 |
| AI活用開発との相性 | 「AIと相性がいい」 | 次節 |

保守性は、PoCの時期がいちばん安く測れます。コードベースがまだ1時間で読める大きさのうちに、書いていない人に小さな変更を渡して時間を計ってください。

## 4つ目の軸は、こう測る

いま多くのチームが、良いほうにも悪いほうにも、これを確かめずに信じています。問いはこうです。**このスタックのコードベースは、その多くがアシスタントによって書かれたとき、どこまで持ちこたえるのか。**

試し方は単純で、同じ機能を候補ごとにアシスタントへ渡します。見るのは出力ではなく**レビュー**です。

```text
[ ] 返ってきたもののうち、正しかった割合／もっともらしく誤っていた割合
[ ] 人間が見る前に、コンパイラや型システムがはじいた件数
[ ] 標準ライブラリで足りたか、依存関係を引いてきたか
[ ] 整形がツールで確定しているか（差分がスタイルの話になっていないか）
[ ] できあがったものをレビューするのにかかった時間
```

最後の行が、チーム規模とともに効いてくる数字です。生成量ではありません。

補足として、公開されたコードが豊富な言語ほどアシスタントは流暢に書きます。ただしそれがすべてではなく、**言語の表面積が広いほど、自信をもって間違えられる場所も増えます**。レビュアーが頭に置いておくものが増える、ということです。

## そのまま使えるPoC計画書

着手前にこれを埋めて、チームで合意してから始めます。埋まらない欄があるなら、それはまだPoCではありません。

```markdown
## PoC: <候補名>

- 問い:        （「いいえ」と答えられる形で）
- 期限:        YYYY-MM-DD（この日に終わる）
- 課題:        （本当に不安な部分。CRUDではない）
- 実装者:      （その候補を推していない人が望ましい）
- レビュアー:  （全候補で同一人物）

### 評価軸と重み（着手前に合意）
| 軸 | 重み | 測り方 |
|---|---|---|
| スケーラビリティ | 3 | 想定の10倍で p95 と月額 |
| 保守性 | 3 | 未経験者が小変更を入れるまでの時間 |
| 速度 | 2 | ベンチ＋チームの書きやすさ |
| AI活用開発との相性 | 2 | 上のチェックリスト |

### 結論（期限日に記入）
- 選んだもの:
- 決め手:
- 何があれば結論が変わるか:
```

最後の行を必ず書いてください。半年後に「なぜこれにしたんだっけ」と訊かれたときに答えられるのは、この一行だけです。

## 「いいえ」と答えてよい

PoCは「すでにあるものを残すか」にも答えます。その案件には1年以上前に一人の開発者が書いた既存のコードベースがあり、これから始める範囲に対しては足場としてほとんど機能しませんでした。これも正当な結論です。ただし、ほかと同じように書かれた問いと期限が必要です。そうでないと、議論はコードではなく前の書き手のほうへ流れます。

答えが出たら、PoCは**消すか、やり残した部分の計画を添えて意図的に育てる**かのどちらかにします。「参考までに」置いておくと、コピーされます。

## PoCが覆わない半分

その案件の言語選定はAI活用開発を織り込んでいました。一方で、それをどう進めるかのワークフローは最初から標準化されておらず、成果物がチームの共通の期待に合わないことがしばしばあり、手戻りが生じ、全体の品質を下げました。

技術評価が答えるのは**どの道具か**です。**どう働くか**には答えません。アシスタントに渡す前のタスクはどういう形か、レビューはこれまで見ていなかった何を見るのか、どこは手で書くのか。2つ目の問いは1つ目と同じだけ意図的に扱う価値があり、たいてい何も与えられません。週末に見せられる成果物がないからです。
