承認も却下も、何かを後に残します。記録、責任者、日付、次に起きること。そのどちらでもない「保留」だけが、何も残しません。何かを置いておくのに最も安く、置き続けるのに最も高い状態です。

そして保留は、チケットの経過日数を見ても良し悪しが分かりません。ここでは、保留をあとから読める状態にするための欄と、技術導入を可逆性で分ける表、そのまま使えるテンプレートを置きます。

## 経過日数は、良い保留と悪い保留を区別しない

| 状況 | 経過 | 評価 |
|---|---|---|
| 依存するアーキテクチャが未決で止まっていた | 数か月 | **正しい** |
| 要件をリリースに入れる唯一の機会を逃した | 3週間 | **まずい** |

同じ指標で、正反対の読み方になります。経過時間は症状であって、原因ではありません。そして原因ごとに、取るべき対応は逆になります。

| 待っている理由 | 対応 |
|---|---|
| まだ解決していない依存がある | 正しい。何を待っているかを書く |
| 今期の優先度として意図的に後回し | 正しい。これも意思決定として記録する |
| 誰にも依頼していない情報待ち | 依頼が欠けている |
| 誰も責任を負っていない判断待ち | 責任者が欠けている |
| 答えが「いいえ」だが言いづらい | 「いいえ」が欠けている |

最後の行が一番高くつきます。「いいえ」は待っている人を解放し、異議も申し立てられ、状況が変われば見直せます。沈黙はそのどれもしないまま、同じ時間を使います。

## 保留に5つの欄を足す

判定の基準は1つだけです。**その場にいなかった人が読んで、自分が動くべきか分かるか。**

```text
NG: ステータス: 保留
```

```markdown
状態:       保留（前提条件待ち）
理由:       基盤の選定結果を待っている
解除条件:   基盤の方針が確定すること ← 日付ではなく条件
責任者:     <名前を1人。チーム名は不可>
再判断日:   YYYY-MM-DD ← 条件が揃わなくてもこの日に見る
今の影響:   なし / <止まっているもの>
```

費用は1文です。これがないと、3か月後に最初の会話を忘れた人へ提案をもう一度説明することになります。同じ議論が二度行われ、二度目は違う結論に着きます。

## 金額ではなく可逆性で分ける

よくある規則は金額の閾値です。ある額までは管理者、超えたら委員会。運用は簡単ですが、測っている性質が違います。**全員の作業手順の中に入り込んだ月額数千円のツールは、その10倍の一度きりの購入よりも抜けるのが難しくなります。**

認証基盤が分かりやすい例です。導入が最も安く、離れるのが最も高く、しかも最初の環境を立てた人が半日で決めてしまいます。請求書を見ても、そのどれも分かりません。

| 種別 | 例 | 判断に必要な材料 | 撤回の仕方 |
|---|---|---|---|
| **A: 上限付きの試行** | ツールの限定利用 | 人数・期間・上限額・答えたい問い | 更新しない |
| **B: 構造的な選択** | 基盤、認証基盤、言語、データモデル | 代替案、評価軸、TCO、PoC | 最初の1つを載せるまでは自由。以降は移行 |
| **C: 顧客への約束** | 契約上の要件、配布済みアプリ、破壊的移行 | 間違っていた場合の立ち位置を先に文書化 | 原則、戻せない |

Aは最も少ないプロセスで足りるのに、最も過剰に管理されがちな種類です。Bの境目は「最初の1つがその上に載った瞬間」で、プロセスを置くべきなのもそこです。Cで問うべきは金額に見合うかではなく、間違っていた場合に自分たちがどういう立場に立つのかです。

## 申請する側の4行

ツールの申請は、2つの主張を含んでいます。そして聞き取られるのは片方だけです。

```text
言いやすい理由:   「これがあると作業が速くなる」
本当に欲しいもの: 「自分が書いていないコードベースを理解する手段」
                  「新しい人が1か月ではなく1週間で貢献を始められる状態」
```

管理側は、聞き取ったほうを評価します。打鍵速度の尺度で見れば「いずれ持っていてよいもの」なので、実装が律速になる時期に合わせて予定されます。双方とも筋は通っていて、それぞれ違う問いに答えています。ずれているのは人ではなく申請の側です。

```markdown
- 課題:       <誰が、どこで困っているか>
- 遅れる費用: <3か月後だと何が違うか>
- 判断希望日: <なぜその日までに必要か>
- 判定指標:   <効いたと分かるために何を測るか>
```

この4行は、相手が**速く「はい」と言える**ようにするための4行でもあります。

## 調べることと、決めることを分ける

「Xを評価する」という1項目は、4つを混ぜています。

```text
1. 知りたいのか          ← 意思決定
2. 誰が調べるのか         ← 作業
3. いつまでにか           ← 作業
4. 答えをどうするのか      ← 意思決定（これが失われる）
```

調査は終わり、答えはコメントに収まり、それが支えるはずだった意思決定は起きません。チケットは2つに分け、2つ目にも期限と責任者を置きます。

もう1つ、**前提より長生きした調査**に注意してください。依存が想定と違う形で解決しても、保留中の項目は自分の想定を保ち続けます。読み返す人がいないからです。ですから「決まった」は、それを待っていた項目を棚卸しする合図にします。意思決定は下された時点ではなく、**待っていたものが更新または終了された時点で終わります**。

## 仕組み自体のコストも測る

ここまでのすべては、やらない場合より仕事が増えます。意思決定ごとに文書を求める仕組みは、速くするために作ったはずの意思決定を遅くします。最初にそれを感じるのは、小さく可逆な選択をしている人たち、つまりその仕組みを最も必要としていない人たちです。

**記録を書く時間が、意思決定にかかった時間より長いなら、記録が長すぎます。** 管理のための工数も、観測する数値の1つに入れてください。

## 4週間で試すなら

制度を作る前に、2〜3件で回してみるのが安全です。

| 週 | やること |
|---|---|
| 1 | 対象を2〜3件選ぶ。現状の状態と経過を記録する |
| 2 | 5つの欄と4行のテンプレートを適用する |
| 3 | 期限内に「承認 / 却下 / 条件付き保留」のどれかにする |
| 4 | 振り返る。速度だけでなく、手戻りと管理工数も見る |

4週間・数件で「平均リードタイムが何%短縮した」と統計的に言うことはできません。確かめるのは**運用できるかどうか**です。速度が変わらなくても、保留の理由と責任者と次の行動が見えるようになったなら、それは十分な第一歩です。
